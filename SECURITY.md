# Security

## Reporting a vulnerability

Please use GitHub Security Advisories (the repository's **Report a vulnerability** action) instead of opening a public issue.

## Threat model

- The bridge binds to `127.0.0.1` only. It rejects requests with a browser `Origin` header and requires `Content-Type: application/json`, preventing ordinary cross-site form/simple-fetch attacks.
- Every route except `/healthz` requires `Authorization: Bearer $CLAUDE_BRIDGE_API_KEY`, compared in constant time. The installer generates a random 32-byte token per install and writes it, mode `0600`, to `~/.hermes/.env` and the launchd/systemd unit. The server refuses to start without a token — there is no unauthenticated mode. `/healthz` stays open: it spends no quota and carries no user content — only a static service name and version, which the installer uses to verify it is talking to the bridge. A local process that can read `~/.hermes/.env` (i.e. anything running as you) can still spend quota.
- Request headers must arrive within 15s and the full request body within 120s, so a stalled client cannot pin a connection open. Neither timeout bounds the streaming response.
- Every Agent SDK child environment removes `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_TOKEN`, `ANTHROPIC_BASE_URL`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX`, and all `ANTHROPIC_VERTEX_*` variables. The prompt is parked behind a gate and is only dispatched after SDK account metadata confirms a first-party Claude subscription — a rejected account never receives user content. The bridge additionally rejects explicit or missing API-key credential sources. Claude Code currently reports `apiKeySource: "none"` for valid Keychain-backed subscription OAuth, so account metadata is the primary check.
- Extra Usage (overage) refusal is **best-effort, not a guarantee**. The Agent SDK offers no pre-flight rate-limit query; the only signal is the in-stream `rate_limit_event`, whose cadence and fields are not contractual. The bridge aborts the turn when metadata reports `isUsingOverage: true` or a rejection typed `overage` (mapped to HTTP 402 so Hermes does not retry), even if text has already streamed. When a turn completes with no rate-limit metadata at all, the bridge cannot prove it ran on subscription quota — it logs a warning that overage state is unverified. A mid-stream overage abort after SSE headers are sent still closes as HTTP 200 with the error surfaced in content, because Hermes was observed to mishandle other framings; the 402 status is only possible before streaming starts.
- The bridge retains the SDK's official Claude Code system-prompt preset and never sets the SDK's `systemPrompt` from inbound `system`/`developer` messages. Both a raw custom prompt and appending the full Hermes harness prompt were observed to route through Extra Usage even for a first-party Max account, so this preset-only behavior and its regression tests are billing-safety boundaries. Inbound system content is delivered as a `<system-instructions>` preamble on the live user turn instead. That preamble was live-checked on 2026-08-02 with a real 35,631-character Hermes harness prompt on `claude-sonnet-4-6` and `claude-opus-4-7`: both turns reported `status: "allowed"`, `rateLimitType: "five_hour"`, `isUsingOverage: false`. Routing is decided by the system prompt, not by user-turn content — but that is an empirical result, not a contract, so re-check it if the preamble format changes.
- OAuth credentials remain owned by Claude Code. The bridge does not copy them into Hermes or its own runtime. When replaying history, the Agent SDK stages a refresh-token-stripped copy of the access token, mode `0600`, in its own temporary directory for the child process.
- Replayed conversation history is held in memory and handed to the SDK through a `sessionStore` adapter, so it is never written into the user's `~/.claude/projects/`. A bridge turn therefore cannot leave a ghost session in the interactive `claude --resume` picker, and an interactive resume in the same working directory cannot collide with a bridge turn. The SDK removes its temporary directory after the child exits; that cleanup runs in the bridge process, so a SIGKILL of the bridge can still leave one transcript and its staged access token in the OS temp directory until the OS sweeps it.
- Default mode disables Claude Code tools, settings, skills, hooks, filesystem/cloud MCP servers, auto-memory, and auto-compaction.
- Tool mode (any request that carries Hermes `tools`) exposes those exact tool schemas to Claude through an in-process MCP server. Claude Code gets no built-in tools (`disallowedTools` covers every Claude Code built-in; `allowedTools` is limited to `mcp__hermes-tools__*`), and the SDK runs under `bypassPermissions` only so tool *calls* need no Claude-side approval — the bridge itself never executes a tool. Every tool call is surfaced to Hermes as an OpenAI `tool_call` and executed by Hermes with its own permissions, logging, and sandboxing; Claude only ever sees the result. The bridge holds the query open across requests while Hermes executes (coordinator TTL 10 minutes, then the query is aborted), so an abandoned round-trip cannot pin a process forever.
- Full-agent mode (`CLAUDE_BRIDGE_FULL_AGENT=1`) was removed in 0.3.0: tool mode supersedes it with a strictly smaller attack surface — Claude's only tool path goes through Hermes, instead of granting Claude Code bypass-permission built-ins.
- Every SDK child environment also drops all `CLAUDE_BRIDGE_*` variables, so a prompt-injected turn cannot read the bridge's bearer token or discover its mode and executable settings.
- The installer writes under `~/.hermes` and the current user's launchd/systemd directories. It runs `npm install` inside `~/.hermes/claude-bridge` to install the pinned Agent SDK and its platform-specific executable; it uses no privileged commands.
